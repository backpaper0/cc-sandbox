# ネットワーク隔離はデフォルトbridge + DOCKER-USER iptablesルールの多層防御とする

検証の結果、Dockerのデフォルトbridgeネットワークだけでも「ホスト側サービスが`127.0.0.1`限定でlistenしていれば」コンテナからは自然に到達不可であること、逆に`0.0.0.0`でlistenしていれば単純に到達できてしまうことを確認した。`--internal`ネットワークはインターネットアクセスも含めて全遮断してしまうため、「サンドボックス→ホストは遮断、インターネットは許可」という要件には合わない。そこで、運用ルール（ホスト側サービスは127.0.0.1限定でlisten）に加えて、`DOCKER-USER`チェーンにサンドボックス用ネットワークからホストのプライベートIP帯への到達を明示的にDROPするiptablesルールを足す多層防御方式を採用する。なお、macOS側でOrbStack/Docker Desktopの`host.docker.internal`がこのルールを迂回しないかは別途実機検証が必要な既知の未検証事項として残っている。

## Considered Options

- `--internal`ネットワーク + 専用egressプロキシ経由でインターネットのみ許可 — 確実だが実装コストが高く、まずは軽量な方式で様子を見ることにした
- 運用ルールのみ（iptablesなし） — うっかり`0.0.0.0`でlistenさせる事故を防げないため見送った

---

**この決定は [ADR-0004](0004-network-isolation-in-container-owner-match.md) に置き換えられた。** 本文中で未検証事項として残していたmacOSでの`host.docker.internal`迂回は、実機検証の結果、実在することが確認された（解決先の`0.250.250.254`はRFC1918の範囲外のため、ここで決めたルールではカバーできない）。加えて、macOSではDocker daemonがVM内で動くためホスト側に`iptables`が存在せず、この方式自体が成立しないことが分かった。ルールをホスト側ではなくサンドボックス本体コンテナの内側に置く方式へ変更している。
