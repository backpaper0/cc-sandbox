# ユーザー入力ターンの通知は、ホスト常駐の「通知ウォッチャー」が`Stop`/`idle_prompt`フックを検知する方式とする

## 背景と課題

cc-sandbox は bypass permissions モードでの利用を前提としており、Claude Code はコマンド実行やファイル削除を確認なしに進める。この特性上、ユーザーは Claude Code を起動しっぱなしにして別作業へ移ることが多い。しかし現状、Claude Code のターンがユーザー側に戻った（＝入力待ちになった）ことを知る手段が無く、気付かずに放置してしまう。

### 伝達方式の検討

最初に検討したのは、Claude Code のフックがターミナルへベル文字（`\a`）を出力し、端末アプリ側の「ベルで通知」機能に委ねる方式だった。macOS（Terminal.app / iTerm2）ではこれだけで Notification Center への通知（バックグラウンドでも）を実現できる。しかし WSL2 の Windows Terminal は BEL に対してタスクバーアイコンの点滅までしかできず、真の Windows トースト通知にはならない。cc-sandbox は私的環境（macOS）・業務環境（WSL2）の両方をホストとして想定しており（[CONTEXT.md](../../CONTEXT.md)の「ホスト」参照）、業務環境側だけ体験が劣化する設計は避けたい。

そのため、ホスト側に常駐する「通知ウォッチャー」プロセスが `docker exec` 経由で本体コンテナ内のフック発火を検知し、ホストOSネイティブの通知（macOS/WSL2 それぞれのAPI）を呼び出す方式を採る。この設計はサンドボックスのネットワーク隔離（[ADR-0004](0004-network-isolation-in-container-owner-match.md)）の非対称性、すなわち「コンテナ→ホストは遮断されているが、ホスト→コンテナの`docker exec`は元々開いている」という既存の前提（`cc-sandbox exec`/`password`と同じ経路）を利用したものであり、新たな穴を開けない。

### トリガーイベントの検討

Claude Code のフックのうち、`Stop`（アシスタントの応答が終わりターンがユーザーに戻る瞬間）と、`Notification`の`idle_prompt`マッチャー（理由を問わず約60秒間アイドルが続いたときに発火）を組み合わせて使う。

`Notification`にはもう1つ`permission_prompt`マッチャーがあるが、bypass permissionsが既定のcc-sandboxでは権限確認そのものがほぼ発生しないため対象外とした。

当初は`Stop`のみで足りると考えていたが、検討の過程で`AskUserQuestion`のようにClaude自身がユーザーに判断を仰ぐツール呼び出しは、フック層からは「ツール呼び出し中」としか見えず、`Stop`はおろか`Notification`も即座には発火しないという Claude Code 自体の既知のギャップが判明した。このケースを拾える唯一の手段が`idle_prompt`（最大60秒遅れ）だったため、これを追加することにした。

### `idle_prompt`の間引き

`idle_prompt`は単発ではなく、ターミナルがフォーカスされていない間、約60秒おきに繰り返し発火する。cc-sandboxの想定利用シーン（別作業中でそのターミナルにフォーカスが戻らない）ではこの条件に常に当てはまるため、素通しすると数分〜数十分にわたって延々と通知が続く。これを避けるため、通知ウォッチャー側で`idle_prompt`由来の通知にのみ5分のクールダウンを設ける。`Stop`由来の通知は常に即時かつクールダウン対象外とし、その発生自体も「最後に通知した時刻」を更新する（`Stop`直後の`idle_prompt`と二重に鳴らないようにするため）。

## 決定

1. **トリガー**: `Stop`（毎回即時）＋ `Notification`の`idle_prompt`マッチャーのみ。`permission_prompt`は対象外
2. **`idle_prompt`の間引き**: 通知ウォッチャー側で5分のクールダウンを設ける。`Stop`はクールダウンの対象外だが、クールダウンのタイマー自体は更新する
3. **伝達方式**: ホスト常駐の「通知ウォッチャー」が`docker exec`経由でコンテナ内のフック発火を検知し、ホストOSネイティブの通知を出す。ベル文字方式は不採用
4. **ライフサイクル**: `cc-sandbox up`の最後にバックグラウンドで自動起動し、`down`で自動停止する。cc-sandbox にとって初めての常駐プロセス管理
5. **`down`時の失敗ハンドリング**: 通知ウォッチャーの停止に失敗しても`down`全体はベストエフォートで続行する。隔離・セキュリティに関与しないただの利便機能であり、[ADR-0004](0004-network-isolation-in-container-owner-match.md)/[ADR-0008](0008-restrict-dev-sudo-to-package-management.md)が守る性質のものとは異なるため、`up`のall-or-nothing（隔離適用等の失敗時は即異常終了）とは意図的に非対称にする
6. **有効化**: デフォルト有効（イメージ焼き込み、フラグ不要）。`cc-sandbox up --no-notify`でインスタンス単位に無効化できる
7. **`-p`（非対話）実行時**: 対話/非対話を区別しない。`-p`でも`Stop`が発火すれば通知するが、実装をシンプルに保つため誤通知の可能性は許容する
8. **`list`表示**: ウォッチャーの状態を`running`/`disabled`（`--no-notify`指定時）/`down`（クラッシュ等）の3値で表示する新しい列を追加する
9. **通知内容**: インスタンス名を含める。ホスト側が既に持っている情報なので、コンテナ側への変更は不要

## 結果として生じること

* 良い点: ベル文字方式に比べ、macOS/WSL2で一貫した体験になる
* 良い点: `AskUserQuestion`待ちも（最大60秒＋クールダウンの遅延はあるが）拾える
* 良い点: `--no-notify`により、通知が不要な場面でもインスタンス単位で止められる
* 悪い点: cc-sandboxに常駐プロセスという新しい管理対象が増える（`up`/`down`の責務拡大、`list`の表示拡張）
* 悪い点: `AskUserQuestion`待ちの検知は`idle_prompt`頼みで、最大60秒＋クールダウン分の遅延が残る。Claude Code側にユーザー入力待ちを直接示すフックが無い限り解消できない
* 悪い点: `-p`実行でも区別なく通知するため、`-p`を連発する自動化用途では誤通知が増えうる（`--no-notify`で個別に回避可能）
* 悪い点: 同一コンテナ内で複数の`docker exec`セッションから並行してclaudeを動かした場合の重複通知・紐付けの曖昧さには対応しない

## 再検討のトリガー

* Claude Code に「ユーザー入力を待っている」ことを直接示すフックイベント（`AskUserQuestion`起因を含む）が追加されたとき。`idle_prompt`頼みの近似が不要になる
* 通知ウォッチャーのような常駐プロセスを必要とする機能が他にも出てきたとき。今回確立する`up`/`down`との統合パターンを再利用するか、より汎用的な仕組みに一般化するかを検討する
